## Architecture / Important Decisions
- `src/turbo-key-installer.mjs`가 helper 자산명·프로토콜 버전, GitHub Release 조회, SHA-256·PE 검증, AppData 원자 설치와 실행 파일·manifest 제거를 소유한다.
- 배포본은 현재 앱 버전 태그의 정식 GitHub Release와 고정 자산명만 허용한다. 설치 상태는 `current.json`의 helper·프로토콜 버전과 실행 파일 해시를 실행 전마다 대조한다.
- `web/TermsModal.svelte`는 고정 header/footer와 부드러운 독립 스크롤 본문을 제공하며 `web/MarkdownBlocks.svelte`가 작동 원리 화면과 약관의 안전한 Markdown 표현을 공유한다. 약관 원문은 `TURBO_KEY_TERMS.md`에서 직접 불러온다.
- `package.json`의 Electron 진입점은 `electron/bootstrap.mjs`다. 부트스트랩은 오류 기록기를 먼저 설치한 뒤 `electron/main.mjs`를 동적 import해 모듈 평가 실패도 기록한다.
- 창 생성·렌더러 로드는 초기 최적화 작업과 분리한다. 정상 경로는 OST 재생 시작 IPC에서 기존 fade-in을 사용하고, 해당 신호가 없으면 생성 후 8초에 같은 표시 함수를 강제 호출한다.
- 최초 `loadAll()`은 시작 화면을 허용한 뒤 별도로 실행하므로 느린 시스템 조회가 있어도 UI가 먼저 나타나며 각 서비스는 기존 loading 상태를 유지한다.
- `native/turbo-key` Rust helper가 `WH_KEYBOARD_LL`로 물리 키를 추적하고 `SendInput`으로 down/up pulse를 보낸다. 주입 이벤트와 Windows 자동 반복은 다시 처리하지 않는다.
- Electron은 선택 키를 검증·정규화해 AppData 설정에 보존하고 helper의 `--keys` 시작 인자로 전달한다. Rust hook은 선택되지 않은 키를 통과시키고 활성 반복을 취소한다.
- Shift/Ctrl/Alt/Win 및 잠금·시스템 키는 제외하며 modifier 입력, 게임 포커스 상실, 부모 앱 종료 시 즉시 반복을 중단한다.
- helper는 Electron이 계산한 게임 외 P-core 마스크를 시작 인자로 받아 즉시 적용한다. Affinity helper도 같은 지연 민감 프로세스 목록을 5초 감시마다 동일한 마스크로 유지한다.
- Electron은 `%APPDATA%/마비노기 렘 부스터/turbo-key`의 settings/status/control JSON으로 설정과 생명주기를 관리하며 트레이 자동 시작과 업데이트 종료에도 동일하게 적용한다.
- affinity 모듈이 CPU 마스크 계산, 프로세스 탐색, 적용·복구, 상태 저장을 소유한다.
- 가장 높은 `EfficiencyClass`를 P-core 계층으로 취급하고 그보다 낮은 계층은 모두 백그라운드 마스크에 포함한다.
- CPU 재정렬은 두 P-core 절반만 교환하며 E-core는 항상 백그라운드 쪽에 유지한다.
- Windows CPU Set 조회가 실패하거나 현재 affinity 그룹과 일치하지 않으면 기존 논리 CPU 절반 마스크로 대체한다.
- 관리자 manifest 앱의 일반 Run 키 자동 실행은 신뢰성이 낮아, Windows Task Scheduler의 현재 사용자 `AtLogOn`·`Highest`·`Interactive` 작업을 사용한다.
- 개발 실행에서는 Electron 개발 런처가 자동 등록되지 않도록 시작 트레이 옵션을 지원하지 않는다.

## Constraints / Rules
- 사용자가 터보 키 속도를 반복 시험하는 동안에는 별도 요청 전까지 커밋하지 않는다.
- Windows x64와 Node.js 20 이상만 지원한다.

## Known Issues
- 기존 공개 0.2.2 설치본에는 선택 다운로드 UI가 없으므로 새 기능 테스트에는 로컬 최신 패키지가 필요하다.

- 터보 키의 hook·주입·종료·CPU 마스크 복구는 독립 helper로 검증했지만 실제 마비노기와 BlackCipher 환경에서의 입력 수용 여부는 수동 검증이 필요하다.
- 반복 입력 도구의 운영정책 위험은 문서에 유지하되 사용자 요청으로 고급 기능의 별도 경고 문구는 표시하지 않는다.
- `runtime-state.json`을 직접 덮어써 동시 읽기 시 일시적으로 불완전한 JSON이 노출될 수 있다.
- 복구 실패 여부와 관계없이 상태 파일을 삭제하는 기존 동작이 남아 있다.
- 실행 중인 기존 인스턴스와 동시에 드라이런했을 때 상태 파일 파싱 오류가 재현됐다.
- 네트워크 모듈 외 기능에는 자동화된 단위·통합 테스트와 CI가 없다.
- 저지연 모드 ID는 NVIDIA 공개 NVAPI가 아니므로 드라이버 변경 시 호환성이 깨질 수 있다.
- 비공개 저지연 값 적용·검증은 NVIDIA Profile Inspector 호환 내부 setter/getter ABI에 의존한다.
- Radeon 설정은 GPU 전역에 영구 유지되어 다른 게임에도 영향을 줄 수 있다.
- Radeon ADLX 실제 쓰기는 전용 Radeon 장비에서 아직 수동 검증하지 않았다.
- 인터페이스 재시작 중 네트워크 연결이 잠시 끊기며 실행에는 관리자 권한이 필요하다.
- Electron 창과 UAC 승격 보조 프로세스는 자동화된 통합 테스트 없이 빌드·구문 검사만 완료했다.
- 현재 TCP 자동 조정은 `Experimental`이며 관리자 권한 적용 전까지 비최적화로 남아 있다.
- NIC RSS 적용·복원은 관리자 권한과 인터페이스 재시작이 필요하다.
- Affinity 장기 실행 helper의 실제 UAC 시작·종료·비정상 종료 복구는 아직 수동 검증하지 않았다.
- 기존 CLI nogirem과 Electron Affinity helper를 동시에 실행하면 서로의 적용 상태를 소유하지 못하므로 함께 실행하지 않아야 한다.
- Electron 메인과 sandbox 렌더러를 포함한 앱 전체가 관리자 권한으로 실행되므로 preload IPC 허용 범위를 계속 제한해야 한다.
- CPU 재정렬의 실제 3초 역전·정상 복귀는 프로세스 affinity를 변경하므로 자동 실행 검증하지 않았고 수동 확인이 필요하다.
- 새 설치 프로그램의 실행 중 앱 정상 종료와 구버전 강제 종료 fallback은 NSIS 컴파일까지 검증했으나 실제 설치 통합 동작은 수동 확인이 필요하다.
- YouTube 직접 조회는 비공개 HTML 구조에 의존하므로 YouTube가 마크업을 변경하면 마지막 캐시로 대체되고 파서 보완이 필요하다.
- 17:53에 시작된 수정 전 관리자 Electron PID 54644가 20:19에도 남아 있으며, 20시 이후 프로세스는 종료돼 단일 인스턴스 재실행이 계속 구버전 창만 포커스한다.
- 개발 실행은 승격 앱 종료를 추적하지 않으므로 Vite 터미널은 별도로 `Ctrl+C` 종료해야 한다.
- 메모리 helper의 실제 게임 감지와 압박 조건 정리는 자동화된 통합 테스트 없이 상태 조회·빌드로만 검증했다.
- NIC RSS를 실제 변경·복원하는 최초 토글은 네트워크 인터페이스 재시작 때문에 빠르게 완료할 수 없다.
- 현재 승격된 Electron PID 52832는 일반 권한 셸에서 종료 권한이 거부되어 사용자가 직접 닫아야 한다.
- 작업 관리자 강제 종료나 프로세스 강제 제거는 웹 모달과 정상 helper 중지를 우회한다.
- `audiodg.exe`를 CPU 0~7로 제한하면 오디오 드롭·지연이 발생할 가능성이 있다.
- 고정 640×290 창에서는 기존 대시보드 전체 내용이 세로 스크롤로 표시된다.
- 시작 음악은 Electron의 미디어 자동재생 정책이나 오디오 장치 상태에 따라 재생이 거부될 수 있다.
- 시작 안정성 회귀는 정적 계약 테스트와 웹 빌드까지 통과했지만 실제 저사양·보안 프로그램 환경의 8초 강제 표시는 설치본 수동 검증이 필요하다.
- 프레임리스 창에는 시스템 최소화 버튼이 없으며 현재 커스텀 UI는 닫기만 제공한다.
- 앱 자동 업데이트는 패키징된 앱에서만 동작하며 GitHub Release에 설치 파일·blockmap·`latest.yml` 세 자산이 모두 있어야 한다.
- Affinity는 기존 단일 프로세서 그룹과 최대 52개 논리 CPU 제한을 유지하므로 다중 프로세서 그룹 시스템은 지원하지 않는다.
- 시작 트레이 예약 작업의 실제 로그온 실행은 설치본과 Windows 재로그인이 필요해 자동 검증하지 않았다.
