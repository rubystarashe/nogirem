쉬운 설명 · 신규 개발자용

컴퓨터 안의 작은 호텔 운영팀

한 문장 요약: Nogirem은 손님이 버튼을 누르면 관제실이 Windows와 여러 전문 기술자에게 안전한 작업만 맡기고, 결과를 다시 화면에 보여주는 관리자 권한 앱이다.

개요기술 구조시각화

호텔 비유

호텔 로비에 있는 안내판이 앱 화면이라고 생각해 보자. 안내판이 직접 객실 전기나 엘리베이터를 고치지는 않는다. 손님의 요청을 관제실에 전달하고, 관제실은 알맞은 기술자를 부른다.

로비 안내판Dioxus UI와 WebView2 창. 버튼·상태·안내를 보여준다. 근거: desktop/src/ui.rs, desktop/src/native.rs
인터폰한 줄씩 JSON을 주고받는 stdin/stdout RPC. 외부 TCP 명령 서버를 열지 않는다. 근거: desktop/src/bridge.rs, desktop/backend/src/rpc.rs
관제실Rust native service. 창, 설정, 최적화, 녹화, 업데이트 요청을 알맞은 모듈로 보낸다. 근거: desktop/backend/src/service.rs
전문 기술자CPU·메모리 worker와 입력·Radeon·녹화 helper. 오래 걸리거나 반복되는 작업을 별도 프로세스로 수행한다. 근거: desktop/backend/src/workers.rs, native/recorder-helper/main.cpp
운영 장부%APPDATA%\마비노기 렘 부스터 아래 JSON 설정·상태·복구 기록. 원자적으로 써서 중간 파일을 정상 상태로 오인하지 않게 한다. 근거: desktop/backend/src/storage.rs, desktop/backend/src/workers.rs
봉인된 교체 부품Ed25519 서명, 정확한 GitHub 주소, 크기와 SHA-256을 확인한 업데이트 파일. 근거: desktop/backend/src/updater.rs

사용자가 앱을 켜면

  1. 같은 앱이 이미 있는지 확인한다.
    한 사용자에게 대화형 인스턴스 하나만 남기고, 두 번째 실행은 기존 창에 포커스 요청을 보낸다. desktop/src/platform.rs
  2. 관리자 권한이 아니면 UAC로 다시 시작한다.
    CPU 선호도, 네트워크, 설치 캐시처럼 시스템 경계를 다루기 때문이다. 계약 검사와 격리 스모크는 예외다. desktop/src/main.rs
  3. 보이지 않는 창과 관제실을 준비한다.
    GUI 프로세스가 같은 EXE를 --native-service 모드로 다시 실행하고, 두 프로세스가 표준 입출력으로 연결된다. desktop/src/bridge.rs
  4. 관제실이 트레이와 메인 창을 연다.
    설정 조회와 최적화 상태 확인을 병렬로 진행하고 준비가 끝나면 시작 화면을 드러낸다. desktop/backend/src/service.rs, desktop/backend/src/service_windows.rs
  5. 버튼 요청을 해당 전문가에게 보낸다.
    예를 들어 실시간 부스트는 CPU worker와 메모리 worker를 관리하고, 블랙박스는 녹화 helper와 미디어 창을 관리한다.
  6. 닫을 때 복구 여부를 묻는다.
    CPU 제한이 남아 있다면 복구 후 종료, 유지 후 종료, 취소 중 사용자가 결정한다. helper를 멈춘 뒤 관제실이 GUI 종료를 요청한다. desktop/backend/src/service.rs

각 기술자가 하는 일

CPU와 메모리

마비노기와 일반 프로그램이 같은 CPU 영역을 두고 다투지 않도록 선호도를 나누고, 메모리가 실제로 부족할 때만 Windows 대기 목록 정리를 시도한다. 게임 메모리를 직접 수정하지 않는다. boost.rs, affinity_worker.rs, memory.rs

네트워크와 그래픽

Windows 네트워크 설정과 드라이버가 제공하는 기능을 사용한다. NVIDIA는 게임 프로필 중심이고, Radeon은 ADLX 제약 때문에 전역 설정이 될 수 있다. network_manager.rs, graphics.rs, dxvk_manager.rs

블랙박스와 입력

녹화와 입력 주입은 별도 native helper가 담당한다. Rust 서비스는 설정·상태·제어 파일과 제한된 채널을 통해 helper를 시작하고 멈춘다. blackbox.rs, inputs.rs

업데이트는 “봉인 확인 후 교체”

앱은 GitHub에서 작은 서명 manifest를 먼저 받는다. 공개키로 서명을 검증하고, 허용된 파일명·주소·버전·크기인지 확인한 다음 큰 EXE를 내려받아 SHA-256을 다시 계산한다. 검증된 파일만 보호된 작업 폴더로 복사한다.

설치형은 NSIS 설치기를 실행한다. 포터블은 사용자가 보관한 단일 EXE를 같은 볼륨의 보호 staging을 거쳐 바꾼다. 새 앱이 UI와 백엔드 준비 신호를 보내지 못하면 이전 파일로 되돌린다. update_install.rs, portable.nsi

이 비유가 맞지 않는 지점

별도 프로세스가 곧 보안 sandbox라는 뜻은 아니다. GUI, native service, worker는 같은 배포 EXE의 여러 실행 모드이며 대화형 앱은 관리자 권한으로 동작한다. 프로세스 분리는 책임·장애·수명 관리를 위한 경계다.
“장부”는 중앙 데이터베이스가 아니다. 기능별 JSON 파일과 상태 파일의 묶음이며, 각 모듈이 정해진 경로를 읽고 쓴다.
확인된 안전 경계: 업데이트는 서명·크기·해시·경로·reparse·integrity·열린 handle을 조합해 검증한다. 단순히 “관리자라서 안전하다”에 의존하지 않는다.
미검증: 자동 테스트는 실제 게임, 모든 GPU 드라이버, 전원 중단, 다양한 Windows/DPI 환경을 전부 재현하지 않는다. DIOXUS_MIGRATION.md의 QA 공백을 함께 봐야 한다.

문서 간 주의할 점

DIOXUS_MIGRATION.md 뒤쪽의 “Rust backend migration in progress” 절은 당시 이행 중 기록이다. 같은 문서 앞부분과 현재 desktop/backend/src/lib.rs·desktop/src/bridge.rs는 현재 native service가 Rust임을 보여준다. 역사 기록을 현재 구조 설명으로 읽으면 안 된다.
