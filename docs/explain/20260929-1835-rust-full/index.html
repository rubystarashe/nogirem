세 가지 읽는 방법

  • 1. ELI5 — 호텔 운영에 빗대어 이해하기

    UI, Rust 서비스, worker, 설정 파일, 업데이트를 “프런트·관제실·기술자·장부·봉인된 택배”에 대응한다. 비유가 틀어지는 지점도 함께 적었다.

  • 2. Understanding — 코드와 책임 경계

    프로세스 구성, stdio RPC, 최적화 모듈, 저장 경로, 관리자 권한, 설치형·포터블 업데이트와 테스트 범위를 파일 근거와 함께 설명한다.

  • 3. Visual — 아키텍처와 핵심 흐름

    외부 viewer 없이 열리는 inline SVG로 실행 구조와 서명 업데이트·롤백 흐름을 표시한다. 모든 연결선에 관계 이름과 방향을 적었다.

분석 범위

  • Dioxus UI와 WebView2 호스트
  • Rust native service와 stdio RPC
  • CPU·메모리·네트워크·그래픽 최적화
  • 블랙박스·입력·선택형 helper
  • 설치형·포터블 실행과 업데이트
  • 설정·상태·복구 파일
  • NSIS 패키징과 서명 manifest
  • 현재 Rust 경로의 테스트와 QA 공백
확인된 사실: 설치물의 앱·서비스 실행 경로는 Rust이며, Node.js는 개발·테스트·패키징 도구로 남는다. DIOXUS_MIGRATION.md와 desktop/src/main.rs에서 확인했다.
범위 제외: Electron 애플리케이션 구현, vendored Dioxus 내부, AMD SDK 원본, 빌드·릴리스 생성물, 과거 AI run은 구조 분석에서 제외했다. 단, 구버전에서 Rust로 넘어오는 migration 경계는 업데이트 호환성 설명에만 포함했다.
미검증: 이 보고서는 코드·계약·테스트 분석 결과다. 실제 게임 실행 중 드라이버 변경, 녹화, 다중 DPI, UAC 취소, 전원 중단 롤백을 새로 실행한 결과가 아니다.

빠른 시작 파일

처음 읽는다면 다음 순서가 가장 짧다.

  1. README.md — 제품 목적과 사용자 기능
  2. desktop/src/main.rs — 프로세스 모드와 GUI 진입점
  3. desktop/src/bridge.rs — GUI가 native service를 시작하는 경계
  4. desktop/backend/src/service.rs — 서비스 조정과 채널 라우팅
  5. desktop/backend/src/update_install.rs — 업데이트·복구 신뢰 경계
